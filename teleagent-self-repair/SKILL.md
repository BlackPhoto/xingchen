# TeleAgent 自我检修技能

> **声明：本技能为 TeleAgent 智能体内置技能，用户无需额外安装。**

## 技能定位

将用户自发的"用 AI 工具修 TeleAgent"行为官方化、规范化。

核心价值：
- **安全兜底** —— 明确哪些能改、哪些绝对不能碰
- **诊断流程化** —— 从"凭感觉改"变成"按步骤查"
- **修复标准化** —— 已知故障模式提供标准修复路径
- **用户确认下自动修复** —— 检测到问题后，向用户展示修复计划，获得确认后自动执行修复

## 覆盖平台与适用范围

- **覆盖平台**：macOS / Windows / Linux（三平台统一逻辑，路径按平台自动适配）
- **适用范围**：软件可启动但存在异常的场景。软件整体无法启动的场景不在本技能覆盖范围内（用户无法调用技能）
- **边界说明**：技能以"软件可启动"为前提，不再单独检查 Electron 主进程——用户能触发技能即说明主进程在运行。若软件整体无法启动，应引导用户收集日志并联系客服支持

## 三平台路径体系

> ⚠️ **TeleAgent 2.6+ 引入多用户子目录结构**：配置、数据、技能、记忆、日志均位于 `users\<当前账号ID>\` 子目录下，而**不是** 直接位于 `~/.config/TeleAgent/` 或 `~/.local/share/TeleAgent/` 根目录。根目录下同名文件为旧版本（≤2.5.x）遗留残留，**不是当前账号生效数据，不得作为修复目标**。所有脚本必须先定位当前账号目录，再在其下操作。

### 当前账号目录定位（三选一，按优先级）

所有脚本一律按以下顺序解析当前账号根目录：

1. **环境变量（最准，TeleAgent 运行时已注入）**：
   - 配置根：`$env:TELEAGENT_CONFIG_DIR` / `$TELEAGENT_CONFIG_DIR`
   - 数据根：`$env:TELEAGENT_DATA_DIR` / `$TELEAGENT_DATA_DIR`
   - 日志目录：`$env:SUPER_AGENT_LOG_DIR` / `$SUPER_AGENT_LOG_DIR`
2. **兜底：读 owner 标记**：解析 `<数据根>/current-owner.json` 的 `ownerDir` 字段（如 `v1_public_2083014823995428864`），拼 `users\<ownerDir>\`。
3. **再兜底：探测活跃子目录**：枚举 `users/` 下子目录，取最近修改的那个作为当前账号。

> 找到的当前账号目录必须满足：配置根下存在 `TeleAgent.jsonc` 或 `skills/`，或数据根下存在 `teleagent.db`/`log/`，否则视为定位失败并回退/提示。日志目录为 `users\<账号ID>\log\`（单数 `log`，不是 `logs`）。

### 三平台目录总览

| 体系 | macOS | Linux | Windows |
| --- | --- | --- | --- |
| 应用安装（只读） | `/Applications/TeleAgent.app/` | `/usr/lib/TeleAgent/` | `%LOCALAPPDATA%\TeleAgent\` |
| 全局配置根 | `~/.config/TeleAgent/` | `~/.config/TeleAgent/` | `%USERPROFILE%\.config\TeleAgent\` |
| 全局数据根 | `~/.local/share/TeleAgent/` | `~/.local/share/TeleAgent/` | `%USERPROFILE%\.local\share\TeleAgent\` |
| **当前账号配置** | `~/.config/TeleAgent/users/<账号ID>/` | 同左 | `%USERPROFILE%\.config\TeleAgent\users\<账号ID>\` |
| **当前账号数据** | `~/.local/share/TeleAgent/users/<账号ID>/` | 同左 | `%USERPROFILE%\.local\share\TeleAgent\users\<账号ID>\` |
| **当前账号日志** | `~/.local/share/TeleAgent/users/<账号ID>/log/` | 同左 | `%USERPROFILE%\.local\share\TeleAgent\users\<账号ID>\log\` |
| Electron userData | `~/Library/Application Support/TeleAgent/` | `~/.config/TeleAgent/` | `%APPDATA%\TeleAgent\` |

> **应用安装目录为只读区域，技能不应对其执行任何写操作。**

## 文件安全分级

> ⚠️ 本节是技能的核心设计，Agent 不得违反。

### 红线区：绝对禁止修改

以下文件涉及认证凭证、加密密钥或核心数据，Agent **不得读取内容更不得修改**：

| 文件 | 禁止原因 | 所属目录 |
| --- | --- | --- |
| `auth.json` | 明文存储 LLM API Key，泄露/删除 = 服务被滥用 | 当前账号数据 `users\<账号ID>\auth.json` |
| `app-auth/state.json` | JWT + deviceId + installId，修改导致认证失效 | 当前账号数据 `users\<账号ID>\app-auth\` |
| `secure-credentials.json` | 加密的企微 BotId/BotSecret | 当前账号数据 `users\<账号ID>\im-service\` |
| `local-secret.json` | 本地加密密钥，删除后所有加密凭证无法解密 | 当前账号数据 `users\<账号ID>\im-service\` |
| `weixin-credential.json` | 加密的微信凭证 | 当前账号数据 `users\<账号ID>\im-service\` |
| `*.db`（所有 SQLite 文件） | 二进制数据库，手动编辑必损坏 | 当前账号数据 `users\<账号ID>\`（含 teleagent.db、scheduler.db、im-service.db 等） |
| `user-agent-config.json`（水印相关字段） | 水印开关涉及 AIGC 合规要求，Agent 不得修改 | 当前账号数据 `users\<账号ID>\user-agent-config.json` |
| `.updaterId` | 更新器设备标识 | 当前账号数据 `users\<账号ID>\.updaterId` |
| `skills-metadata.json` | 注册技能必须走 IPC/API，直接编辑会导致元数据不一致 | 当前账号数据 `users\<账号ID>\skills-metadata.json` |

**红线区允许的唯一操作**：检查文件是否存在（`Test-Path` / `test -f`）。对 `*.db` 文件额外允许 `sqlite3` 只读查询（如 `PRAGMA integrity_check`）。

**特别说明**：
- `user-agent-config.json` 中除水印字段外的其他字段（如 `preventSleepDuringTasks`）属于绿色区，Agent 可正常读取和建议修改。但任何涉及水印开关的操作均为红线，必须引导用户通过客户端 UI 操作。
- **数据库修复为显式例外**：检查项 3（`repair-db-corruption`）是对 `*.db` 的显式修复例外，须走「用户确认 → 备份三件套 `.db/.db-wal/.db-shm` → 三级修复 → 逐级验证 → 回滚兜底」完整流程（详见 `references/repair-db-corruption.md`）。本例外与上文「红线区只读」不冲突：未经用户确认与完整流程，Agent 不得直接删除/改写任何 `.db`。

### 黄色区：可修改但需谨慎

| 文件 | 修改注意事项 | 所属目录 |
| --- | --- | --- |
| `TeleAgent.jsonc` | 写入非法字段会导致 Server fatal 退出。修改前必须备份 + JSON 校验 | 当前账号配置 `users\<账号ID>\TeleAgent.jsonc` |
| `custom-tool-sandbox.json` | 禁用工具影响 AI 能力，模板改错可能引发安全漏洞 | 当前账号配置 `users\<账号ID>\tools\` |
| `channel-config.json`（IM） | 渠道开关可改，但结构不可乱 | 当前账号数据 `users\<账号ID>\im-service\` |

**黄色区标准修改流程**：1. 备份原文件（.bak）→ 2. 执行修改 → 3. JSON 格式校验 → 4. 重启服务验证

### 绿色区：可放心修改

| 文件/目录 | 说明 | 所属目录 |
| --- | --- | --- |
| `TeleAgent.jsonc`（permission 部分） | 技能权限 allow/deny 控制（仅此部分按绿色区处理，其余字段仍按黄色区） | 当前账号配置 `users\<账号ID>\TeleAgent.jsonc` |
| `TeleAgent.jsonc`（disabled_providers） | 禁用 LLM 提供商（同上，仅此部分按绿色区） | 当前账号配置 `users\<账号ID>\TeleAgent.jsonc` |
| `skills/` 目录 | 技能文件的增删改 | 当前账号配置 `users\<账号ID>\skills\` |
| `memory/` 目录 | USER.md、MEMORY.md、每日日志 | 当前账号数据 `users\<账号ID>\memory\` |
| `user-agent-config.json`（非水印字段） | preventSleepDuringTasks 等功能偏好 | 当前账号数据 `users\<账号ID>\user-agent-config.json` |

### 运行时自动维护区

以下运行时状态文件 Agent **可读取获取诊断信息，不需要也不应该引导用户修改**（改了也会被下次启动覆盖）：

- `session-status.json`
- `onboarding.json`
- `updater.json`
- `super-agent.pid`
- `wecom-state.json`
- `weixin-state.json`
- `scheduler-daemon-state.json`

## Agent 行为规范

> ⚠️ 以下约束写死在本文件中，Agent 不得违反。

1. 修改任何配置文件前，**必须先创建 .bak 备份**
2. 修改 `TeleAgent.jsonc` 后，**必须执行 JSON 校验确认格式合法**
3. **绝对禁止直接编辑 .db 文件**，如需查询数据使用 `sqlite3` 只读命令
4. **绝对禁止修改红线区任何文件的任何字段**
5. **绝对禁止修改水印开关**，必须引导用户通过客户端 UI 操作
6. 清理缓存/日志前，**必须明确告知将删除哪些文件、释放多少空间**
7. 如发现用户数据有被误改风险，**优先引导备份而非直接修复**
8. 遇到无法处理的深层问题，**引导用户收集日志并联系客服支持**
9. **涉及重启 TeleAgent 的修复步骤，Agent 不得主动执行**——杀死 TeleAgent 进程会导致 Agent 自身终止。Agent 应提示用户执行此步骤会终止 TeleAgent 进程，给用户提供"是/否"确认选项，由用户决定是否执行；用户选"是"后，Agent 可调用重启脚本执行（脚本作为独立进程继续完成重启动作，Agent 会话随之中断），用户需重新打开 TeleAgent 后再次触发自检完成验证。
10. **两段式修复门禁（分级执行）**：所有由 Agent 动手执行的修改类操作（黄色区/绿色区文件改写、缓存清理、数据库重建等），执行前必须先向用户输出修复计划（修改对象、影响范围、可释放空间、是否可回滚、将执行哪些命令），等待用户明确同意后再执行。涉及终止/重启 TeleAgent 的命令已在第 9 条单独约束（需用户"是/否"确认），此处不再重复门禁要求，但修复计划中仍需列出这些命令告知用户。
11. **references 章节级加载**：当检查项标注"失败时加载 `references/xxx.md#章节名`"时，按文件内 `##`/`###` 标题文本定位到该小节阅读，不整文件加载；仅当该小节内引用了其他步骤或其他文件时，再按引用展开。若未提供章节名，则加载整个文件。
12. **分级备份替换流程**：按文件重要性选择修改方式（用户已明确授权此分级策略）：
    - **重要文件——走完整备份替换流程，保留副本**：指改坏会导致 TeleAgent 无法启动或数据丢失的用户系统文件，包括黄色区全部（`TeleAgent.jsonc`、`custom-tool-sandbox.json`、`channel-config.json`）、数据库（`*.db`）、以及任何删除红线区文件操作涉及的目标文件。流程：① 复制原文件为 `.bak`（保留不删，作为回滚点）→ ② 在 **副本**（如 `<文件>.new`）上执行修改 → ③ 验证（按文件类型：JSON 校验 / 语法解析 / `PRAGMA integrity_check`）→ ④ 验证通过后用 `Move-Item -Force`（或 `mv`）原子替换正式文件 → ⑤ 原正式文件改名降级为 `.bak`（**保留不删除**）。修复脚本（check/fix-teleagent-jsonc、mcp-check/fix-jsonc、mcp-fix-paths、db-repair）内置的备份/回滚逻辑即为此档，保持不动。
    - **其他文件——直接在原文件上修改，不产生任何备份/副本**：包括技能自身文件（SKILL.md、`references/`、`scripts/`）、`memory/` 记忆文件等绿色区文件（用户明确要求目录保持干净）。要求：① 修改前先读取目标区域原文（保留在会话上下文中）→ ② 直接编辑原文件，**不得产生任何 `.bak` / `.new` / 临时目录副本** → ③ 改后验证（`.ps1` 必须过 PowerShell 语法解析，`.sh` 必须 `bash -n`，Markdown 检查章节/表格结构完整；含中文注释的 `.ps1` 必须为 UTF-8 **带 BOM**，否则 PowerShell 5.1 按 ANSI 误读中文注释会引发不受控的语法错误）→ ④ 验证失败时按上下文中的原内容立即恢复本次修改并如实报告，不得盲目重试。
    - **二进制数据库（*.db）**：禁止文本替换。走"备份 `.db/.db-wal/.db-shm` 三件套 → 重建新库 → 验证 `PRAGMA integrity_check` → 替换"流程，原库保留为备份。（属重要文件档）
    - **删除红线区文件不可回滚**：任何涉及删除 .db / 认证 / 密钥类文件的修复，必须向用户明确说明"删除将丢失哪些数据、重启后自动重建"，用户确认后方可执行，且被删文件先备份保留。（属重要文件档）
13. **无既定方案时的一次交互（不强行解决）**：当检测到问题但本技能无对应修复方案时（如日志出现未收录的 fatal/crash，或问题不在任何检查项范围内），**禁止静默跳过或强行尝试**。必须：
    - **Step 1 加一次用户交互**，向用户说明：
      > 当前 TeleAgent 自我检修技能没有针对这个问题的现成修复方案。您可以选择：
      > ① 我根据经验 + 网络搜索，帮您尝试排查解决（可能无法 100% 解决）；
      > ② 联系客服人员处理。
    - **Step 2**：若用户选①，则**基于经验 + 网络搜索**排查，最多尝试 **1~2 次**。每次尝试都必须是**独立、可回滚、用户可见**的操作（先备份、小范围验证），且**不得触发红线区写操作**。
    - **Step 3**：尝试 1~2 次仍未解决，**停止**，明确告知用户：
      > "针对您的问题，当前未找到合适的解决方案。我们会持续优化此技能，敬请期待。您可先联系客服人员解决。"
    - **绝不强行解决**：不得因为"已开始尝试"就持续反复操作或扩大范围到未确认的区域。
14. **破坏性操作护栏（写死，不得违反）**：
    - **黑名单命令**：`rm -rf`、`Remove-Item -Recurse`、`rd /s /q`、`Format-*`、`Del /F /S /Q`、清空回收站等破坏性命令，**除非**技能内某检查项明确声明且获得用户确认，否则 Agent 一律不得调用。
    - **破坏性操作四要素**（缺一不可，全部满足才动手）：① 操作对象明确；② 影响范围明确；③ 可回滚（执行前先备份）；④ 用户明确同意。
    - **网络搜索建议 ≠ 直接执行**：从网络/经验获得的操作建议，必须先在当前账号的**副本/临时目录**上小范围验证无害，确认后再进入正式路径；禁止未经验证直接对正式文件/系统执行。
    - 任何删除/覆盖/清理/重启/系统级修改，必须先展示修复计划（对象、范围、可释放空间、是否可回滚、将执行的命令），获得用户同意后执行。

## 检查项总览

本技能包含 8 个检查项，每个检查项对应 `references/` 下的一个修复方案文档和 `scripts/` 下的诊断/修复脚本。

| # | 检查项 | 参考文档 | 诊断脚本 | 修复脚本 | 操作类型 | 是否需用户确认 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 日志异常检测 | `check-log-anomalies.md` | `check-log-anomalies.ps1` / `.sh` | 无（只读检测） | 纯只读 | 否（仅告知结果） |
| 2 | 磁盘空间清理 | `clean-disk-space.md` | `check-disk-usage.ps1` / `.sh` | 动态生成清理脚本 | 检测 + 清理 | 是（清理前需确认） |
| 3 | 数据库损坏修复 | `repair-db-corruption.md` | `db-check.ps1` / `.sh` | `db-repair.ps1` / `.sh` | 检测 + 修复 | 是（修复前需确认） |
| 4 | MCP 配置格式修复 | `repair-mcp-jsonc.md` | `mcp-check-jsonc.ps1` / `.sh` | `mcp-fix-jsonc.ps1` / `.sh` | 检测 + 修复 | 是（修复前需确认） |
| 5 | MCP 配置路径修复 | `repair-mcp-path-error.md` | `mcp-check-paths.ps1` / `.sh` | `mcp-fix-paths.ps1` / `.sh` | 检测 + 修复 | 是（修复前需确认） |
| 6 | TeleAgent.jsonc 全面检查 | `repair-teleagent-jsonc.md` | `check-teleagent-jsonc.ps1` / `.sh` | `fix-teleagent-jsonc.ps1` / `.sh` | 检测 + 修复 | 是（修复前需确认） |
| 7 | 正在运行的软件与显存占用 | `check-running-software.md` | `check-running-software.ps1` / `.sh` | 无（只读检测） | 纯只读 | 否（仅告知结果） |
| 8 | 代理问题协助 | `proxy-assist.md` | `check-proxy.ps1` / `.sh` | `fix-proxy.ps1` / `.sh` | 检测 + 协助 | 选代理/启动代理需确认；补 NO_PROXY/清残留执行时告知 |

> **脚本命名约定**：Windows 脚本为 `.ps1`（PowerShell 5.1+），macOS/Linux 脚本为 `.sh`（Bash，macOS 和 Linux 合并，通过 `uname -s` 区分路径）。
> **脚本执行约定**：所有脚本相对于技能根目录执行，如 `.\scripts\check-log-anomalies.ps1`（Windows）或 `./scripts/check-log-anomalies.sh`（macOS/Linux）。

### 检查项之间的关系

```
                    ┌─────────────────────┐
                    │ 1. 日志异常检测(只读) │ ← 入口：从日志中找问题线索
                    └────────┬────────────┘
                             │ 日志中发现的错误类型
           ┌─────────────────┼─────────────────┐
           ▼                 ▼                  ▼
   ┌───────────────┐ ┌──────────────┐  ┌────────────────┐
   │3.数据库损坏修复│ │6.配置全面检查 │  │2.磁盘空间清理  │
   └───────┬───────┘ └──────┬───────┘  └────────────────┘
           │                │
           │     ┌──────────┼──────────┐
           │     ▼          ▼          ▼
           │  ┌────────┐ ┌────────┐ ┌────────┐
           │  │4.MCP   │ │5.MCP   │ │(路径   │
           │  │格式修复│ │路径修复│ │ 修复)  │
           │  └────────┘ └────────┘ └────────┘
           │
           ▼
   磁盘空间不足可能导致
   数据库写入失败 → 联动 2

   ┌─────────────────────────────┐
   │7.正在运行的软件与显存占用(只读)│ ← 独立入口：查看运行软件/GPU显存
   └─────────────┬───────────────┘
                 │ 电脑卡慢时可联动 2
                 ▼
           磁盘空间清理

   ┌─────────────────────────────┐
   │8.代理问题协助(检测+协助)      │ ← 独立入口：网页打不开/想开代理
   └─────────────────────────────┘
        （连不上时需排查网络/代理）```

**关键联动关系**：
- **检查项 6（TeleAgent.jsonc 全面检查）** 包含格式检查 + 字段检查 + 路径检测。其中路径问题检测到后，修复需联动 **检查项 5（MCP 路径修复）** 执行（需生成修复清单 JSON + 运行 mcp-fix-paths 脚本）。
- **检查项 4（MCP 格式修复）** 是检查项 6 中格式检查部分的独立实现，功能重叠。用户只需格式检查时用 4，需要全面配置检查时用 6。
- **检查项 1（日志异常检测）** 是最佳诊断入口——日志中的错误信息可直接指向具体故障类型（数据库错误 → 联动 3，配置错误 → 联动 6，磁盘空间 → 联动 2）。
- **检查项 3（数据库修复）** 和 **检查项 2（磁盘清理）** 存在因果关系：磁盘空间不足可能导致数据库写入失败，若数据库检查未发现损坏但用户反馈写入失败，应联动磁盘空间检查。
- **检查项 7（正在运行的软件与显存占用）** 是独立入口的纯只读检查项，与其他检查项无前置依赖。用户说"电脑卡"时，检查项 7 可联动 **检查项 2（磁盘空间清理）**——若发现内存占用高但无明显资源大户，可能是磁盘空间不足导致虚拟内存频繁换页。
- **检查项 8（代理问题协助）** 是以 TeleAgent 正常可用为前提的系统级检查项，独立入口。用户说"网页打不开/想开代理/代理残留"时进入；基础排除发现非代理/断网/DNS问题只做定位不修；启动代理后必须做存活自检，失败则先 repair 再自检，仍失败才 rollback。代理流程决策点一律用 TeleAgent 原生选项卡片呈现（详见 `references/proxy-assist.md`「交互规范」）。

## 意图识别与路由

> 本节在技能加载后指导 Agent 识别用户意图并选择路由策略。

### 一、不触发的情况

以下情况**不触发**检修流程：
- 用户询问 TeleAgent 的使用方法（如"怎么创建定时任务""怎么配置 MCP"）→ 正常回答使用问题
- 用户反馈的是 TeleAgent 功能本身的限制（如"能不能支持xxx功能"）→ 正常回答
- 用户要求修改配置文件的具体内容（如"帮我把 MCP 的 timeout 改成 120000"）→ Agent 直接修改，修改后可选择加载检查项 6 验证格式
- 软件整体无法启动（用户无法与 Agent 对话）→ 引导用户收集日志联系客服支持

### 二、路由决策流程

```
用户消息
  │
  ▼
1. 识别用户意图（匹配检查项 / 多项关联 / 意图宽泛）
  │
  ▼
2. 选择路由策略
  │
  ├── 意图明确，只指向一个检查项 ──────→ 单文件路由
  ├── 意图涉及多个关联检查项 ─────────→ 多文件路由
  └── 意图宽泛（体检/全面检查/不知道）─→ 全文件路由
  │
  ▼
3. 按路由结果加载 references 文档
  │
  ▼
4. 按文档流程执行检测 → 展示结果 → 用户确认 → 执行修复
```

### 三、单文件路由

用户问题明确指向某一类故障，只需加载一个参考文档即可解决。

| 用户意图 / 关键词 | 加载文件 | 说明 |
| --- | --- | --- |
| 出错 / 崩溃 / 闪退 / 启动失败 / 有没有异常 | `check-log-anomalies.md` | 纯只读检测，不修改文件。检测结果可能引导到其他检查项 |
| 磁盘空间不足 / C盘满了 / 清理缓存 / 清理垃圾 | `clean-disk-space.md` | 检测 + 清理，清理前需用户确认 |
| 数据库坏了 / 定时任务失效 / IM授权失效 | `repair-db-corruption.md` | 检测 + 三级修复，修复需关闭 TeleAgent |
| 改了MCP配置想检查格式 / 格式对不对 | `repair-mcp-jsonc.md` | 仅检查 JSONC 格式语法（BOM、全角、尾逗号等） |
| MCP 连不上 / MCP 报错 / 工具连不上 | `repair-mcp-path-error.md` | 检查 MCP 配置中的路径是否存在 |
| 改了配置文件想全面检查 / 配置有没有问题 | `repair-teleagent-jsonc.md` | 格式 + 字段 + 路径全面检查（路径修复联动检查项 5） |
| 看看在跑什么软件 / 电脑好卡 / 显存占用 | `check-running-software.md` | 纯只读检测，列出运行中的软件和 GPU 显存占用 |
| 网页打不开 / 想开代理 / 代理残留 / 代理配置有问题 / 连不上网 | `proxy-assist.md` | 基础排除 + 代理检测，协助（决策用原生卡片，选代理/启动代理需确认，补 NO_PROXY/清理执行时告知） |

**单文件路由执行逻辑**：
1. 加载对应的 `references/xxx.md` 文件
2. 按文档中的"修复流程"章节逐步执行
3. 如检测中发现需要联动其他检查项，转为多文件路由

### 四、多文件路由

用户问题可能涉及多个方面，或一个问题的根因需要多个检查项配合排查。

| 用户意图 | 加载文件 | 联动逻辑 |
| --- | --- | --- |
| TeleAgent 写入失败 / 数据库报错（不确定是数据库损坏还是磁盘空间不足） | `repair-db-corruption.md` + `clean-disk-space.md` | 先运行 db-check 检查数据库是否损坏。若数据库未损坏，再运行 check-disk-usage 检查磁盘空间是否不足（磁盘空间不足是数据库写入失败的常见原因） |
| 日志异常且涉及数据库错误（日志中含 database / SQLite 关键词） | `check-log-anomalies.md` + `repair-db-corruption.md` | 先运行 check-log-anomalies 从日志定位异常原因。若日志指向数据库问题，再运行 db-check 做完整性检测 |
| 日志异常且涉及配置错误（日志中含 fatal / Server fatal / config 关键词） | `check-log-anomalies.md` + `repair-teleagent-jsonc.md` | 先运行 check-log-anomalies 从日志定位异常原因。若日志指向配置问题，再运行 check-teleagent-jsonc 做配置检查 |
| 日志异常且涉及磁盘空间（日志中含 disk / space / ENOSPC 关键词） | `check-log-anomalies.md` + `clean-disk-space.md` | 先运行 check-log-anomalies 从日志定位异常原因。若日志指向磁盘空间问题，再运行 check-disk-usage 做空间评估 |
| MCP 配置相关问题（不确定是格式还是路径） | `repair-mcp-jsonc.md` + `repair-mcp-path-error.md` | 先运行 mcp-check-jsonc 检查格式。格式通过后，再运行 mcp-check-paths 检查路径 |
| 配置文件全面检查（发现路径问题需修复） | `repair-teleagent-jsonc.md` + `repair-mcp-path-error.md` | 先运行 check-teleagent-jsonc 做全面检查（格式+字段+路径检测）。若检测到路径问题，加载 repair-mcp-path-error.md 按其流程生成修复清单并运行 mcp-fix-paths |
| 电脑卡慢（不确定是软件占资源还是磁盘空间不足） | `check-running-software.md` + `clean-disk-space.md` | 先运行 check-running-software 查看哪些软件占用资源。若无明显资源大户，再运行 check-disk-usage 检查磁盘空间是否不足 |

**多文件路由执行逻辑**：
1. 按联动逻辑中的顺序，依次加载并执行每个检查项
2. 前一个检查项的结果可能影响后续检查项是否需要执行（如数据库未损坏则跳过数据库修复，转为磁盘检查）
3. 所有检查完成后，汇总各检查项结果，统一输出报告

### 五、全文件路由

用户要求全面检查、体检，或不确定问题出在哪里，需要逐一排查所有检查项。

| 用户意图 | 加载文件 |
| --- | --- |
| "帮我全面检查一下 TeleAgent" / "帮我体检" / "全面看看有没有什么问题" / "不知道什么问题，帮我看看" / "自检一下" | 全部 8 个参考文档 |

**全文件路由执行顺序**：

> 按以下顺序逐一执行，每项检查完成后收集结果，最终汇总为一份完整报告。

| 顺序 | 检查项 | 加载文件 | 执行内容 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 日志异常检测 | `check-log-anomalies.md` | 运行 `check-log-anomalies` 脚本，从日志中找问题线索 | **第一步执行**：纯只读，无风险。日志中的错误信息可直接指向后续检查项的重点 |
| 2 | 磁盘空间清理 | `clean-disk-space.md` | 运行 `check-disk-usage` 脚本，评估磁盘空间 | 基础健康检查。磁盘空间不足是多种问题的根因 |
| 3 | 数据库损坏修复 | `repair-db-corruption.md` | 运行 `db-check` 脚本，检查数据库完整性 | 数据健康检查。注意：修复操作需要关闭 TeleAgent，全面体检阶段只做检测，修复留到用户确认后执行 |
| 4 | TeleAgent.jsonc 全面检查 | `repair-teleagent-jsonc.md` | 运行 `check-teleagent-jsonc` 脚本，检查格式+字段+路径 | 配置健康检查。此步已包含格式检查（检查项 4 的能力）和路径检测 |
| 5 | MCP 配置路径修复 | `repair-mcp-path-error.md` | 若第 4 步检测到路径问题，运行 `mcp-check-paths` 脚本确认 | **条件执行**：仅当第 4 步发现路径问题时加载。若第 4 步路径检测通过，跳过此步 |
| 6 | MCP 配置格式修复 | `repair-mcp-jsonc.md` | （通常可跳过） | **通常跳过**：第 4 步的格式检查已覆盖此检查项的能力。仅当第 4 步格式检查发现问题但用户只需单独修复格式时加载 |
| 7 | 正在运行的软件与显存占用 | `check-running-software.md` | 运行 `check-running-software` 脚本，列出运行中的软件和 GPU 显存 | 纯只读，无风险。全面体检时的环境快照，帮助判断资源瓶颈 |
| 8 | 代理问题协助 | `proxy-assist.md` | 运行 `check-proxy` 脚本，检查网络/代理状态 | 纯只读检测，修复/协助留待用户确认后执行 |

**全文件路由注意事项**：
- 全面体检阶段（Step 1-4）只做**检测**，不做**修复**。所有检测完成后，汇总问题列表，统一向用户展示修复建议
- 检测阶段发现的问题按优先级排序：P0（立即修，如数据库损坏）/ P1（尽快修，如配置格式错误）/ P2（有空修，如磁盘空间清理）
- 用户确认后，按优先级逐项执行修复，每项修复前展示修复计划并等待确认
- 涉及重启的修复（数据库修复、配置修复）集中在最后统一提示用户重启

## 诊断检查流程

### 一、单项检查通用流程

无论加载哪个检查项，均遵循以下通用流程：

```
Step 1  加载参考文档 → 确认检测脚本和执行步骤
Step 2  运行诊断脚本 → 脚本自动定位文件、执行检测、输出结构化 JSON 结果
Step 3  Agent 解析脚本输出 → 判断是否存在问题
Step 4  向用户展示诊断结果 → （如有问题）展示修复计划，等待用户确认
Step 5  （用户确认后）运行修复脚本 → 脚本自动备份、修复、验证、回滚兜底
Step 6  告知用户重启 TeleAgent 生效（如修复涉及需重启的配置/数据库）
Step 7  （用户重启后）运行诊断脚本二次验证 → 确认问题已解决
```

> **纯只读检查项（检查项 1）例外**：日志异常检测只执行 Step 1-3，不涉及修复。Agent 根据日志结果判断影响并告知用户后续操作。

### 二、全面自检流程

当用户要求全面检查时，执行以下完整流程：

```
Phase 1：信息收集（只读，无风险）
  ├── 运行 check-log-anomalies 脚本 → 收集日志中的异常线索
  ├── 运行 check-running-software 脚本 → 收集运行中的软件与显存占用快照
  └── 从日志线索中标注后续重点检查方向

Phase 2：基础健康检测
  ├── 运行 check-disk-usage 脚本 → 磁盘空间评估
  └── 运行 db-check 脚本 → 数据库完整性检测

Phase 3：配置健康检测
  ├── 运行 check-teleagent-jsonc 脚本 → 格式 + 字段 + 路径全面检查
  └── （若上步发现路径问题）运行 mcp-check-paths 脚本 → 路径确认

Phase 4：汇总报告
  ├── 合并所有检查结果
  ├── 按优先级排序问题（P0/P1/P2）
  ├── 输出结构化自检报告（见"输出规范"）
  └── 等待用户选择修复项

Phase 5：逐项修复（用户确认后）
  ├── 按优先级展示每项修复计划
  ├── 获得用户确认后执行修复脚本
  ├── 每项修复后验证
  └── 涉及重启的修复集中提示

Phase 6：重启后验证（用户重启后再次触发）
  └── 重新运行相关检测脚本，对比修复前后状态
```

### 三、日志驱动的动态路由

当检查项 1（日志异常检测）发现异常时，Agent 应根据日志中的错误类型，主动引导到对应检查项：

| 日志中的错误关键词 | 引导到的检查项 | 说明 |
| --- | --- | --- |
| `database disk image is malformed` / `database is locked` / `no such table` | 检查项 3：数据库损坏修复 | 数据库文件损坏 |
| `Server fatal` / `config` / `mcpServers` | 检查项 6：TeleAgent.jsonc 全面检查 | 配置文件格式或字段错误 |
| `spawn ENOENT` / `path not found` | 检查项 5：MCP 配置路径修复 | MCP 路径写错 |
| `ENOSPC` / `disk full` / `no space left` | 检查项 2：磁盘空间清理 | 磁盘空间不足 |
| JSON parse error / syntax error | 检查项 4：MCP 配置格式修复 | 配置文件 JSONC 格式错误 |
| `proxy` / `ECONNREFUSED` / `tunnel` / `health check failed` | 检查项 8：代理问题协助 | 代理配置/网络问题 |
| 其他未识别的 fatal / crash / panic | 告知用户原因 + 建议重启或联系客服支持 | 不在本技能覆盖范围 |

> **动态路由执行方式**：先完成当前检查项的流程（告知用户日志检测结果），然后告知用户"检测到 [xxx] 相关问题，建议进一步检查 [yyy]"，加载对应检查项文档继续排查。
